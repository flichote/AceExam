# ADR-0001：科目模板化 —— subject 作为一等数据维度

- **状态**：Accepted（M1 基线）
- **日期**：2026-08-07
- **决策者**：ep-arch（评审：ep-backend / ep-db / ep-ai）

## 背景（Context）

AceExam 切入策略是先做公共科目（高数、英语）并**两科并行**（PRD §1.4 科目拍板 2026-08-07），随后扩展到线代、概率论、大物、专业课。核心产品形态"知识点图谱 + 题库 + AI 讲解三件套"在科目间高度同构。

若按科目复制代码（高数一套、英语一套），将导致：
- 双份维护成本，任何算法/页面改动要做两遍
- 新科目扩展成本线性增长，与"模板化低成本扩展"目标冲突

## 决策（Decision）

1. **subject 作为数据模型的一等维度**：内容类实体（knowledge_points / questions / question_embeddings / document_chunks / wrong_answers）全部带 `subject_id` 外键，两科数据物理隔离、逻辑同构。
2. **科目模板 = 数据维度 + 配置维度**：`subjects.config`（JSONB）承载科目级差异（prompt 模板、题型枚举、公式开关、章节结构），代码不因科目分支。
3. **三件套共用代码**：图谱 CRUD、题库/刷题流程、选题算法、RAG 讲解管线、前端页面全部按 subject_id 参数化；仅 prompt 模板与内容数据不同。
4. **新增科目 = 数据 + 配置**（插 subjects 行 + 灌图谱/题库/语料），零后端代码改动；出现全新题型交互（如英语听力播放）才需前端扩展，且须显式评审。

## 备选方案（Considered）

- **按科目复制服务/前端**：维护成本翻倍，否决。
- **多租户式 schema 隔离**：为科目建独立表集，过度设计，否决。
- **纯配置驱动无 subject 表**：科目语义散落各处，无法支撑隔离与统计，否决。

## 后果（Consequences）

- **正面**：新科目边际成本低（数据+配置）；两科共享 bug 修复/算法升级；统计报表天然按 subject 聚合。
- **代价/风险**：所有查询多一个过滤维度，必须防止漏过滤造成跨科数据串扰（API 契约强制 `subject_id` 参数）；`type` 枚举需按科目配置扩展，需在选题/解析逻辑处做配置读取而非硬编码。

## 验收标准（Verification）

- [ ] `subjects` 表含高数、英语两行，`config` 有模板配置
- [ ] 全部内容表带 `subject_id` 且索引覆盖
- [ ] 换一个 subject_id 查询，全链路（图谱/题单/RAG）不串数据
